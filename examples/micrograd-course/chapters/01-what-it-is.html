A trail of breadcrumbs

In ordinary Python, 4 + 2 gives you 6, and the 4 and the 2 are gone. The answer has no memory of its parents.

micrograd refuses to forget. Every result keeps a pointer back to the numbers that made it — breadcrumbs dropped on the way out, so the trail can be walked backwards later.

Code micrograd/engine.py, lines 13-22 
    def __add__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data + other.data, (self, other), '+')

        def _backward():
            self.grad += out.grad
            other.grad += out.grad
        out._backward = _backward

        return out
In plain English
  1. This runs every time you write a + b and a is one of micrograd's numbers.
  2. If you added a plain 2, quietly wrap it first, so everything downstream can assume it is dealing with the same kind of thing.
  3. Make the answer — and notice it stores three things, not one: the sum, who its two parents were, and the label '+'.
  4. Now write the note-to-self: when someone eventually tells me how much I mattered, here is how I pass that message back to my parents.
  5. For addition the answer is beautifully lazy. Nudge the sum up by one and each input contributed exactly one, so both parents get the message unchanged.
  6. Staple that note to the answer and hand it back.

A function defined inside another function, still alive after the outer one has finished, is called a A function that remembers the variables that surrounded it when it was created, even after that surrounding code has finished. Step through what Python builds when you write one short line.

  1. Python evaluates a * b first, making a new number that remembers a and b.
  2. That temporary number is then added to c, making a third number.
  3. d holds 18.0 and the entire family tree hangs beneath it.

That family tree has a name engineers use constantly: a Directed acyclic graph: a set of things joined by one-way arrows, with no way to loop back to where you started. A family tree is one; a circular argument is not.. Saying "micrograd builds a DAG of scalar operations" to an assistant gets you a far more precise answer than "it does the maths thing".

Decision

Scalars, not tensors — every number is its own object

README.md — "The DAG only operates over scalar values… potentially useful for educational purposes"

What was chosen

One Value per number; a neuron becomes visible adds and multiplies.

What was rejected

Tensors — whole grids of numbers moved at once, the way every production framework works.

What it costs

Speed, catastrophically — an object and two closures per operation.

Revisit it when

Never — the README says educational. When speed matters, the answer is PyTorch.

The wrapping trick has a mirror image: it also works when the plain number comes first.

How it actually works

Write 2 * x and Python asks the number 2 to multiply first — and 2 has never heard of Value. Python then tries the reflected version, __rmul__, on x, and engine.py defines the full set: __radd__, __rsub__, __rmul__, __rtruediv__. Each just flips the operands and reuses the normal path, so both orderings build the same graph.

A performance-minded engineer

An object allocation and two closures for every single addition? This is the least efficient arithmetic ever written. Why would anyone study code that no one would ever ship?

Answer it in your head first. Then check.

How you would answer

Because the inefficiency is the pedagogy. PyTorch does conceptually identical bookkeeping — a graph of operations, each remembering its inputs and how to push gradients back — but buried in C++ and batched over tensors, where no one can watch it happen. micrograd unrolls the same machine into 94 readable lines. You study it precisely because it makes the invisible thing visible; you ship the other one.

What will not survive: "it could be optimised later". The follow-up is then why hasn't anyone? — the honest position is that its slowness is a deliberate, stated trade for legibility, not a gap waiting for a patch.
